01 · The problem

AI can build a feature in minutes. Do you know why it works?

  • What does await actually pause, and what keeps running meanwhile?
  • Why does this condition use <= and not <?
  • What does this LEFT JOIN do to rows with no match?
  • What happens when this promise is rejected, and who catches it?

The gap

The code runs, so you move on. The next time it breaks, you have no mental model of the mechanism underneath, and you cannot debug it.

Ask the room: who has accepted AI-written code that they could not fully explain? Let the question land before the next slide.
02 · The solution

A learning panel next to the conversation, not inside it

01

Observe

Watches the exact edits Claude makes to your files and detects the programming mechanisms behind them.

02

Explain

Lessons anchored to a file and a line number: the mechanism, the reason, the alternatives and the common mistakes.

03

Check

Exercises on your own code, and a knowledge model that tracks what you can actually do, not what you have clicked.

Nothing is added to the conversation or to Claude's context. Lessons appear only in the Mentor panel, so your normal work with Claude is unchanged.
Stress the three verbs: observe, explain, check. Each maps to a part of the system we will see later.
03 · How it works

From one edit to a stored skill

  1. Claude edits a fileEdit, Write or a Bash command
  2. Read the diffExact patch from the tool result, not from git
  3. Detect conceptsExplicit rules for JS, TS, Python, PHP, SQL, Dart and Flutter, with the line number
  4. PrioritiseWhat you do not know yet comes first; mastered concepts are skipped
  5. LessonBuilt-in lesson always; AI adapts it to your code when the budget allows
  6. ExercisePredict, diagnose or explain behaviour in your own code
  7. Model updatedStored in local SQLite. Level rises only on graded answers
Key rule: when Claude uses a concept in your project, it counts as encountered, never as known. Only your own answers raise your level.
Walk through the seven steps left to right. Emphasise step 2 (exact diff) and the final rule: exposure is not understanding.
04 · Feature: Change Lab

Every change Claude makes, explained

  • Grouped by your prompt, with the exact code before and after.
  • A lesson on the change: the mechanism, the reason and what to watch out for.
  • Run & compare: both versions run on the same inputs. For x < 10 changed to x <= 10, the boundary value 10 is added automatically and the difference is shown.
  • Another approach: one or two genuinely different solutions, with pros, cons and when to choose each.
Show the difference between a generic tutorial and this: the example is the code Claude just wrote in your project, on the line where it was written.
05 · Feature: Execution simulator

Step through the code, one line at a time

  • Step forward and back through JavaScript, TypeScript and Dart, or press Play.
  • Variables, the call stack and the event loop (microtask and macrotask queues) update at every step.
  • What-if: change one operator or value to create variant B and compare the two outcomes.
  • Deterministic and sandboxed. It never runs your code in your real environment and never edits project files.
Be explicit about the limit: it is a model of a subset of the language, not the real runtime. Network calls, randomness and time are marked as assumptions.
06 · Feature: Learning model

A knowledge model based on evidence, not on clicks

LevelWhat it takes

Can applyMastery ≥ 65%, 2+ good answers, one from a task that requires thinking
Partly understoodMastery ≥ 35% and at least 1 good answer
LearningA lesson, an exercise or a simulator experiment
Not knownNo evidence yet
  • 89 concepts in a dependency graph, e.g. functions → callbacks → Promise → async/await → event loop.
  • Spaced repetition, SM-2 style, so concepts come back before you forget them.
  • Misconceptions are tracked, for example confusing = with ===, or off-by-one errors with < and <=. They are practised until they disappear.
The design choice to defend: the level is earned from graded answers only. Opening a lesson or seeing a concept in code does not count.
07 · Feature: Context bar

See your context budget above the prompt

  • Context usage split into categories (system, tools, MCP, skills, messages), with a tooltip for each.
  • Prompt-cache countdown: how long until the next message is cheap again.
  • Warning zones at 60% and 80% of the window.
  • Computed locally from the /context estimate, so the bar makes no extra API calls.
This is a small feature with a clear purpose: it makes cost and context visible while you work, instead of after the bill arrives.

09 · Architecture

A plugin with one small database helper

  • hooks/register.tsxIntegration: session start, prompt submit, tool calls, turn complete, the /mentor command
  • hooks/mentor.tsController: observations, priorities, lesson queue, exercises. Helpers in hooks/core/
  • hooks/engine/Concept detection, diff reading, secret redaction, lessons, quizzes, cost budget, graph
  • hooks/sim/Lexer, parser, interpreter with an event loop, Dart translator, value semantics
  • hooks/ui/Panel views, the context bar and the topic line above the prompt
  • hooks/content/The 89 concepts: explanations, misconceptions and questions
  • helper/mentor-db.mjsSQLite via node:sqlite: migrations, WAL, transactions, mastery model, spaced repetition

About 24,700 lines of TypeScript in the hooks. Stack: Claude Code hooks, TypeScript, Node.js 22.5+, SQLite.

Point at the split between the UI and the engine. The engine is pure logic and is what the tests exercise most.
10 · Key design decisions

Three choices that shaped the system

DECISION 1

Changes come from tool results, not from git

Edit and Write return the exact patch and the original file. Mentor reconstructs nothing, and it never attributes your earlier edits or another session's work to Claude.

DECISION 2

No daemon, no background service

The plugin host has no Node runtime, so the database is a short process per batch of operations (about 110 ms). No port, no process to babysit. Parallel sessions coordinate through SQLite WAL and busy timeouts.

DECISION 3

AI is optional

Built-in lessons, the simulator, quizzes, history and progress all work without a model. AI only deepens lessons and grades open answers.

These three decisions answer the questions people usually ask: why not git, why not a server, and what happens offline.
11 · Privacy and cost

Local by default, with a daily budget for AI

Privacy

  • Local only. No telemetry, no sync, no external servers.
  • Sensitive files skipped: .env, keys, certificates, credentials, .ssh and similar.
  • Secrets removed before saving and before any AI call: API keys (Anthropic, OpenAI, Stripe, Google, AWS), GitHub and Slack tokens, JWTs, passwords in URLs.
  • A "don't send code" setting sends only the description to the model.

13 · Honest limitations

What it does not do yet

  • The simulator models a subset of JavaScript, TypeScript and Dart. It is not the real runtime, and network, randomness and time are flagged as assumptions.
  • Dart numbers: int and double are one number in the simulator, so 6 / 2 shows 3, not 3.0.
  • Flutter UI cannot be executed. The widget tree is shown, but not rendered.
  • Language split: the interface and AI lessons follow the English setting, but the built-in lesson library is still in Polish.
  • Redaction is pattern-based. An unusual secret format can get through.
  • Platforms and requirements: Claude Desktop on Windows and macOS, Claude Code CLI on Linux, and Node.js 22.5 or newer.
Naming limitations first is a strength in a university presentation. It shows you know where the boundaries are.
